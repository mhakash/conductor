# 0009 — Workflows as YAML

Status: accepted (2026-10-06)

How to write one is documented in [workflow-yaml.md](../workflow-yaml.md).

Workflows can be viewed and edited as YAML in the editor, exported as a
`.yaml` file and imported as a new workflow. YAML is the format for people;
the stored definition stays JSON (ADR 0002), and the server converts between
them so the format is defined once (`internal/wfyaml`).

```yaml
conductor: 1
name: Release
inputs:
  - name: version
    type: text
steps:
  - id: tag
    block: shell
    config:
      command: git tag v$VERSION
      env: { VERSION: "{{ inputs.version }}" }
  - id: notify
    block: workflow
    needs: [tag]
    config:
      workflow: Notify
```

- **`conductor: 1`** marks the document and its format version; anything
  else is refused.
- **Dependencies are `needs` on each step**, as in GitHub Actions, rather
  than a separate list of edges: easier to read and to edit by hand.
- **Canvas positions are left out.** They are noise to a reader; imported
  steps are laid out in columns by dependency depth. Applying edited YAML in
  the editor keeps the position of every step that already existed.
- **Config keys follow the block's form order**, empty values are left out
  and multi-line strings (commands, scripts) are written as literal blocks.
- **Called workflows are written by name** when the name is unique, so a
  file works on another machine; on import a name or an id is accepted, and
  a name must match exactly one workflow.
- **Unknown keys are errors**, with the line, so a typo like `stpes` isn't
  silently dropped. Imports are validated exactly like a save.

Editing YAML in the editor changes the draft only; saving is unchanged, with
its conflict check. Run history keeps its JSON snapshots.

Rejected: storing YAML as the source of truth (comments and formatting would
need preserving through canvas edits), and converting in the browser (a
second implementation of the format to keep in step).
